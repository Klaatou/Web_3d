## 1. Le projet

Une région OpenSim (`.oar`) devient une **page web 3D** où l'on se promène : conversion en glTF (`.glb`), tuiles pour les régions énormes, avatars des autres visiteurs, chat, portails et zones, rien à installer pour les visiteurs. Dépôt public `github.com/Klaatou/Web_3d` (MIT). Klaatou travaille sous Windows (PowerShell, AZERTY, très légèrement daltonien : jamais d'information portée par la seule couleur) ; public visé : communauté OpenSim, surtout anglophone. **Démo** : `https://klaatou.github.io/Web_3d_demo/` (cinq régions reliées par portails : PalmIsland, hobbit, ShowRoom3D, houses, Sandbox_BMoG ; carte des mondes ; présence). Dépôt local : `P:\_OpenSim\SL&OS\Web_3d\web_3d` ; sites de Klaatou : `P:\_OpenSim\SL&OS\Web_3d\Sites` (une coquille `index.html`, `lib\`, `regions.json`, `carte.html`, un dossier par région).

## 5. Décisions de conception arrêtées (ne pas rediscuter sans demande de Klaatou)

**Touches** (même lettre en AZERTY et QWERTY sauf la marche ; **M se reconnaît par le caractère imprimé**) : F ou P entre/sort de la promenade (dans le viewer P pose une zone, on en sort avec F ou Maj+P) ; marche = codes physiques WASD (donc ZQSD) et flèches ; Maj ou double appui = courir ; Espace = sauter ; Début, bouton ou Page Haut maintenu 0,4 s = voler ; Page Haut/Espace et Page Bas/C en vol ; **E** (et clic) = action d'une zone ; **V** = vue subjective / 3e personne / caméra libre ; **M** bascule subjective-3e personne en promenade, ouvre la carte hors promenade ; Ctrl+M carte partout ; molette, Alt+glisser, Fin pour la caméra ; **Entrée** ouvre et envoie le chat (les flèches marchent pendant la saisie), Échap ferme ; **G** bascule la capture de souris (un clic ne capture jamais ; Échap libère) ; **R** retour à l'arrivée ; **H** aide, **I** informations / état, **L** arrivées, **O** réglages, **T** cônes de portail (masque toujours tout), **K** pavé de flèches à l'écran, **B** bloc de chat (replier / déplier). Bouton « Recentrer la vue » (pas de touche).

**Comportements**
- Arrivée `default` = point d'entrée ; `#spawn=NOM` ou `#pos=x,y,z,yaw` ; arrivée occupée : décalage 1,5 m. Région par défaut (sans `?region=`) : `X.config.json` du nom de la page, puis `default.json`, puis `regions.json` ; `?region=` accepte `nom` ou `dossier/nom`, jamais `..`, `:`, `\`, `?`, `#`. Paramètres d'adresse séparés par `&` ou `#` (`#lang=en`, `#name=`, `#pseudos=CLE`). Lien `#spawn=` sur une région en **tuiles** : pas de fond noir pendant le chargement.
- Zones d'une région en tuiles : repère d'origine, liées à un objet par `extras.ref`. Fichiers `X.zones.json`, `regions.json`, `*.html`, journaux : jamais dans le dépôt. Tout texte visible passe par `tr()` / `data-i18n*` (jamais de français en dur). Chat : 200 messages d'historique par défaut ; le serveur jette les messages espacés de moins de 0,7 s (`--chat-gap`) et au-delà de 5 par 10 s ; flèches dans le texte pendant la saisie ; bip à chaque message sans focus (au plus un toutes les 2 s) ; pseudo cité : clignotement jusqu'à la première action.
- **Bloc de chat repliable (B)** : sans délai ni case de Réglages ; un message, une arrivée ou un départ le déplie ; replié seulement par l'utilisateur ; état dans `localStorage` (`web3d.chat.fold`). Aide : touches en gras.
- **Deux philosophies** : (1) **autonome** (pages `.html` fabriquées, tout dedans) ; (2) **hébergée** (coquilles `index.html` et `carte.html` communes lisant `NOM.config.json`, `regions.json`). Les deux cohabitent.
- **Noms** : options, valeurs, clés JSON, paramètres d'adresse en **anglais** ; un nom renommé garde l'ancien en alias (`ANCIENS` de `tests/samples.py` et `REFERENCE_JSON.md` § 11.11). Tout champ JSON ajouté va dans `REFERENCE_JSON.md` (FR et EN) et dans `docs/samples/` (`tests/samples.py` exige les clés exactes de `build_cfg`).
- **Icône de page** : `favicon.ico` à côté de la page s'il existe, sinon le PNG intégré ; sphère seule (1.11.8). **Icône « Réalisé avec Web_3d »** (`#credit`, 32 px, sous le chat, pas dans le viewer) : retirable par `--no-credit` (clé `credit: false`, écrite seulement dans ce cas ; `"credit": false` à la racine de `regions.json` pour la carte).
- **GIF animés** : la page les décode elle-même (`decodeGif` : Chromium ne donne que la première image d'un GIF dessiné sur un canevas) ; PNG et WebP animés non traités.
- **Zones d'image** : cibles sans extension (la page essaie jpg, jpeg, png, webp, gif, avif ; le `.jpg` gagne).
- **Tuiles** : `tiles` est un chemin relatif simple (`safeRel`) ; **pas d'adresse externe sans décision de Klaatou** (étude `ETUDE_MEGAREGION.md` approuvée, aucun code).
- **Paquets** (`galerie-photos.zip`, `region-simple.zip`) : lanceurs Windows, Linux, macOS ; mise à jour d'un paquet publié : **ne jamais dézipper par-dessus**, copier `index.html`, `carte.html` (+ `favicon.ico`, `aide.html`, `regions.json`, `lib\`, `presence_server.py` selon le cas).
- **Zones** (sept genres : `url`, `ha`, `portal`, `spawn`, `image`, `cast`, `audio`). **`url`** : `trigger` `click` / `enter` / `both` (marcher dessus voulu pour `hop://`) ; clé `cone` zone par zone (`true` / `false`, absente = comportement d'avant). **`cast` (radio)** : flux Icecast / SHOUTcast dans `streams` (paires `[nom, adresse]` ; anciennes clés `urls` + `labels` + `target` lues et converties), portée jusqu'à 200 m (50 pour les autres), ni clic ni invite ni lien à un objet, vue globale muette, ne joue pas dans le viewer, cône par défaut ; volume `max(0,05, 1 − d/portée)` x volume radio / musique de la fenêtre Son (50 par défaut) ; une seule radio à la fois ; **titre du morceau lu par le serveur de présence** dans le flux (ICY), jamais par la page, **liste `--radios` obligatoire**, adresse identique au caractère près ; **pas de contournement d'un 403**, pas de relais `http` ; Icecast plutôt que YouTube. **`audio`** : `folder` (cherché d'abord dans `medias/NOM` puis `NOM`) + `playlist.json` (`--audio-list` ou bouton du viewer) ou `tracks` saisi à la main ; ordre alphabétique, nombres comparés comme nombres, boucle, reprise à la piste quittée, zone la plus proche seule ; cases Radio et Musique des Réglages **exclusives** (égalité : radio).
- **Radio à plusieurs flux (1.11.13, `streams` depuis 1.11.26)** : tableau `streams` de paires `[nom, adresse]`, le nom d'abord (`""` sans nom ; 500 flux, 60 car. le nom, 600 l'adresse ; une adresse vide retire sa paire), seule forme écrite (viewer, `--update`, `--zones`) ; `clean_zones` (Python) et `cleanZone` (JS) restent miroirs ; la bulle de la ligne Radio donne le `label` de la zone puis le flux actif, et commence par le flux si la zone a `"label": ""` (voulu par Klaatou) ; liste de choix dans la fenêtre État, **erreur mémorisée par zone et par flux**, quitter la zone ramène au premier flux. **Distance et hors de portée (1.11.17 à 1.11.20)** : la ligne affiche `(37 m / 50 m)` ; au-delà de la portée elle reste jusqu'à **2 fois la portée** (estimation à calibrer), flux arrêté, distance qui **clignote** par l'opacité (jamais par la couleur ; `prefers-reduced-motion` : gras et souligné) ; case de la ligne et boutons ⏮ ⏭ avec compteur n/N pour la musique ; info-bulle native (`title`) sur les lignes ; tout est local, rien n'est envoyé au serveur. La page ne demande le titre que si le flux est réellement écouté, avec 1,5 s d'écart (le serveur ignore un message `radio` reçu moins d'1 s après le précédent, retrait compris).
- **Fenêtre Son, pavé, volume (1.11.24 à 1.11.29)** : quatrième fenêtre (H, I, L, S) qui reprend les lignes Radio et Musique de la fenêtre État (qui ne changent pas) ; la flèche ▲ des lignes l'ouvre **et ferme État**, la croix la ferme, **un clic sur le cône d'une zone radio ou audio à portée** l'ouvre ou la ferme (ce clic n'est plus signalé au serveur) ; taille qui suit le contenu, redimensionnable, dans le fichier de disposition ; titre « Son · Radio » ou « Son · PL Audio » (zone active). **Pavé de flèches déplaçable** par une poignée (`glb2html_padPos`, double-clic = retour, dans la disposition). **Volume** : icône haut-parleur (SVG noir, 0, 1 ou 2 ondes) à gauche de la croix de Son, curseur de 1 à 100, **50 par défaut**, clé `srcVolume` de `glb2html_visitor` (hors disposition), **indépendant** du volume des Sons de Réglages (qui ne règle plus que les bips ; sans valeur retenue, `srcVolume` reprend ce volume) ; couper = la case de la ligne.

## 8. Mécanique de livraison (déplacée de `REGLES.md` le 17/11/2026, lot 1.11.31)

*Comment un lot se fabrique et se livre. Les règles de conduite (honnêteté et méthode, accord avant livraison, format des commandes, réponses courtes, noms, comparaison des livrables, relecture du LLM local, proposition de reprise) restent dans `REGLES.md`, fichier du Projet : la règle 25 cite des noms qu'on ne peut pas écrire dans ce dépôt public.*

### 8.1 Cadre et particularités

- **Bac à sable** : voir § 7 ; dire à chaque livraison ce qui n'a **pas** pu être essayé (Windows, Edge, carte graphique ; convoar tourne avec Mono 6.8, installé par apt-get).
- **Aucune adresse IP ni nom d'hôte réel dans le dépôt** : écrire `ADRESSE`.
- **Klaatou est très légèrement daltonien et utilise un clavier AZERTY** : se méfier des couleurs (jamais d'information portée par la couleur seule) ; l'interface doit marcher en AZERTY et en QWERTY.
- **Décisions de conception arrêtées** : § 5 ; ne pas les rediscuter sans que Klaatou le demande.
- **`REPRISE.md`** vit à la racine du dépôt, sans adresse IP, nom d'hôte ni initiales de Klaatou. Il n'est livré **pas** à la fin de chaque lot, seulement quand Klaatou le demande (après la proposition de reprise, ou à tout autre moment), **en entier**, et il le commite. Entre deux reprises, `CHANGELOG.md`, `CHANGELOG.fr.md` et `git log` font foi. Dans les fichiers du Projet ne reste que `REGLES.md`, qui est stable.

### 8.2 Livrer une modification

- **Un seul passage contigu** : donner le texte exact avant et après ; vérifier que « avant » est unique dans le fichier et qu'aucun des deux textes ne contient d'emoji hors BMP ; Klaatou le remplace à la main.
- **Plusieurs passages, ou un emoji** : `patch_NOM.py`, lancé d'une ligne depuis la racine du dépôt (`P:\_OpenSim\SL&OS\Web_3d\web_3d`), écrit en ASCII (non-ASCII en `\uXXXX`), compatible Python 3.8. Il vérifie la version attendue (`VERSION`) ; il vérifie que chaque passage existe **exactement une fois**, sinon il s'arrête sans rien toucher ; il opère en octets (fins de ligne d'origine préservées, normalisation LF pour comparer) ; il valide `.decode('utf-8')` avant d'écrire ; il propose `--dry-run` ; il garde une copie de chaque fichier modifié dans `_bak\CHEMIN.bak-AAAAMMJJ-HHMMSS` (séparateurs du chemin remplacés par `__` ; dossier dans `.gitignore`). Un fichier nouveau livré avec le patch se range par la même ligne : `Move-Item ".\NOM" ".\tests\NOM" -Force; python .\patch_NOM.py --dry-run; if ($LASTEXITCODE -eq 0) { python .\patch_NOM.py }`.
- **Jamais de fichier complet pour du code existant** (règle 12) ; un **nouveau** fichier (document, traduction, outil) et `REPRISE.md` se livrent en entier. Remplacement de code indispensable : script d'installation qui vérifie l'empreinte SHA-256 du fichier remplacé.
- **Les patchs visent `src\`, `tools\`, `tests\` et les documents, jamais `dist\`** (fabriqué par `python build.py`). `dist\` est suivi par git (depuis la 1.1.6) : après le build il se commite avec le lot (`git add -A`), et `python .\tests\dist_a_jour.py` doit passer avant le commit. **`VERSIONS.json` est écrit par `build.py`, jamais par un patch** (sauf reconstitution décidée avec Klaatou) ; il se commite avec le lot.

### 8.3 Avant toute livraison

Patch appliqué à un clone frais de `main` ; `python build.py --vendor` (jsDelivr est refusé dans le bac à sable) ; syntaxe vérifiée (`python -m py_compile`, `node` pour le JavaScript) ; tests ciblés **et ceux de toute la famille concernée** ; `smoke` ; `dist_a_jour` quand le lot change du code fabriqué ; la suite complète en arrière-plan quand le temps le permet. Dire lesquels ont tourné et lesquels non. Bac à sable : `npm install three@0.160.0` donne le dossier de `--vendor` ; `pip install playwright websockets` (sans `websockets`, les tests de présence échouent par « presence_server ne démarre pas »). Les échecs déjà présents sur `main` sont signalés comme tels, avec la preuve (même test lancé sur `main`).

### 8.4 Ce que donne chaque livraison

- Les fichiers touchés ; la ligne du patch, celle du build, celle du commit, **chacune dans son bloc, seule la première commençant par le `cd`** vers la racine du dépôt (`git add` nomme les fichiers touchés ; au-delà de 8, `git add -A` ; **la ligne du commit ne contient jamais `git status`** : `git status --short`, s'il est utile, se donne avant, dans son propre bloc). Quand le build a modifié `dist\`, la ligne de commit le prend (`git add -A`) et la livraison dit quels fichiers de `dist\` ont changé (liste « modifié dans ce lot » du build). L'étiquette seulement quand une version est publiée.
- **Chaque fichier livré** (patch, test, document, `VERSIONS.json`) est présenté en téléchargement ; vérifier qu'il l'est avant d'écrire « livré ».
- **Une entrée datée par patch dans chacun des deux CHANGELOG** (`CHANGELOG.md` anglais sous « Unreleased », `CHANGELOG.fr.md` français sous « Non publié »), même titre et mêmes identifiants techniques.
- **Version par fichier** : chaque fichier de `dist\` affiche son propre numéro, qui ne change **que** si le contenu de CE fichier change (hors sa ligne de version). Mécanisme (depuis le lot 1.0.4) : `build.py` fabrique tout avec un numéro neutre, compare l'empreinte de chaque fichier à `VERSIONS.json` et n'attribue le numéro du lot qu'aux fichiers dont l'empreinte a changé ; il affiche le numéro de chaque fichier. Les tests lisent `VERSIONS.json`, pas `VERSION`. **Avant toute livraison, vérifier sur le clone, après build, que les fichiers non modifiés ont gardé leur numéro, et le dire.**
- **`VERSION` est seulement le compteur de lots** : chaque patch livré prend le numéro de correctif suivant ; le patch contient le passage `VERSION` (ancien vers nouveau, avec la date), vérifie la version attendue avant de toucher quoi que ce soit, et la ligne de commit nomme `VERSION` (et `VERSIONS.json` si le build l'a modifié). L'étiquette et la publication ne changent que lorsque Klaatou décide une publication, jamais de mon initiative.
- **Avant de donner une ligne de patch, de build ou de commit** : cloner `main` et vérifier ce qui y est déjà ; ne jamais redonner une étape déjà faite ni demander à Klaatou de contrôler à ma place.
- Numérotation `MAJEUR.MINEUR.CORRECTIF` : les correctifs des lots s'enchaînent entre deux publications ; à la publication, si des fonctions ont été ajoutées, le mineur monte et le correctif revient à zéro ; s'il n'y a que des correctifs, elle garde le correctif du dernier lot ; un changement qui casse l'existant (renommage sans alias, format incompatible) donne `2.0.0`. Les étiquettes `v14` à `v52` restent telles quelles (ligne de correspondance dans `CHANGELOG.md`) ; les patchs `patch_vNNx.py` et les tests `tests/vNN.py` gardent leurs noms.
